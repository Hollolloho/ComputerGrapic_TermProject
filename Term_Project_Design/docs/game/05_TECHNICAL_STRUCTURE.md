# 최소 구현 구조

제품 코드는 이 문서 정리에서 수정하지 않았다. 아래는 앞으로 적용할 설계다.

## 출발점과 파일 수

현재 실습은 x64 구성에서 Pratice_10.cpp를 실행하고 다른 main은 제외하는 설정이었다. 구현 시작 시 다시 확인한다. 게임용 main 하나만 빌드되도록 하고 실습 파일은 보존한다.

처음에는 game/main.cpp에서 창·큐브·루프를 검증한다. 기능이 생기는 순서대로 Camera.h/.cpp, Scene.h/.cpp, GameData.h/.cpp를 추가한다. 화면 처리가 길어지면 UI를 분리한다. 처음부터 Renderer·Interaction·EchoController·Audio 등 모든 빈 파일을 만들지 않는다.

| 책임 | 최소 데이터 |
|---|---|
| 카메라 | playerPosition, yaw, pitch, eyeHeight, FOV, 별도 orbit 데이터 |
| 장면 | 큐브 mesh 공유, 물체 ID·변환·색·충돌·조사 ID, 현재/과거 목록 |
| 진행 | 증거 4개 획득 여부, 주장 선택, 정답 완료 여부, 월드·UI 상태 |
| 콘텐츠 | NPC 2명의 고정 대사, 카드 4개, 주장 3개, 결과 문장 |

부모 행렬 조합은 Camera 내부의 명시적인 계산으로 충분하다. 범용 장면 그래프나 데이터 편집기는 필요 없다.

## 화면과 한글

처음에는 고정 패널과 숫자키 선택을 사용한다. 한글 도구는 첫 단계에서 짧은 문장을 출력하는 실험으로 결정한다. 자체 글꼴 엔진을 만들지 않는다. 도구를 연결하기 어려우면 대사·카드의 고정 한글 패널을 미리 만든 텍스처로 표시하는 경로를 사용할 수 있다. 후자의 폰트와 이미지 생성 도구의 조건도 확인한다.

선정한 방식은 실행 파일과 같은 리소스 경로에서 동작해야 한다. 게임에 여러 UI 라이브러리를 동시에 넣지 않는다. UI 선택 결과와 실제 버전을 실행 문서에 적는다.

## 3D와 상호작용

단일 큐브 mesh를 위치·크기·색으로 재사용한다. Model/View/Projection을 구분하고 깊이 테스트를 켠다. 창은 유리 대신 벽의 빈 구멍으로 만든다. 플레이어는 평평한 바닥에서 단순 XZ 부피 충돌을 사용한다. 점프·중력·계단은 넣지 않는다.

광선은 카메라 중심에서 시작하고 가장 가까운 가림 물체를 먼저 확인한다. 대상에는 거리 제한을 둔다. 상세보기 복사본에는 탐색 조사 이벤트를 연결하지 않는다.

단서 관찰 E 입력은 개발 데이터의 고정 설명을 수첩에 남기는 기능이다. 카메라가 자동으로 “증언 거짓”을 판단하지 않는다.

## 렌더링 순서

이벤트, 경과 시간, 모드별 입력, 전환 업데이트, 이동·충돌, 조사 판정, 3D, 안개, UI, 화면 표시 순이다. Inspection 모드면 독립된 단서 배경과 카메라를 그리며 월드 입력을 정지한다.

테두리 안개는 전체 화면 사각형의 가장자리 알파 셰이더다. 중앙에서 테두리까지의 거리와 부드러운 움직이는 무늬로 표현한다. 안개 동안 깊이 쓰기를 끄고 블렌딩을 켠 다음 다음 3D 렌더링 전에 상태를 복구한다. 창의 높이가 0이면 투영 계산·렌더링을 건너뛴다.

## 리소스와 도구

기존 GLFW·GLEW·GLM을 우선 사용한다. FMOD는 소리를 도입할 때, Assimp는 외부 OBJ를 도입할 때 사용한다. 버전·라이선스·런타임 파일의 구체적인 조건은 현재 검증되지 않았으며 실제 연결 시 공식 문서로 확인한다.

게임 셰이더·폰트·패널은 실행 파일 옆 assets 폴더 기준으로 찾는다. 상대 경로는 IDE 작업 디렉터리에 우연히 맞는 상태로 두지 않는다. 파일 로딩 실패는 대상 경로와 함께 표시한다.

현재 프로젝트를 CMake로 옮기거나 라이브러리를 설치하는 작업은 이번 설계 정리에 포함하지 않는다.
