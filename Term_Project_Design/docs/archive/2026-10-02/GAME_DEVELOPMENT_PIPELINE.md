- 문서 버전: 1.2
- 작성일: 2026-09-30
- 기준 기획: [GAME_DESIGN_DRAFT.md](GAME_DESIGN_DRAFT.md), v1.2
- 목적: 초보 개발자 두 명이 작업 순서, 구현 범위, 역할, 완료 기준을 공유하고 제출 가능한 게임을 완성한다.

## 1. 프로젝트 목표와 제약

### 1.1 완성할 게임

중세 유럽풍 마을에서 기억을 잃는 주민들의 증언과, 실제 과거를 보존한 ‘잔향’을 비교하는 3D 1인칭 추리 게임이다. 과거는 정지된 3D 공간이며 플레이어가 직접 걸어 다니며 관찰한다. 과거의 물건을 움직이거나 역사를 바꾸지는 않는다.

핵심 시연은 다음과 같다.

> NPC가 “창밖에서 피해자를 봤다”고 증언한다. 플레이어가 잔향에 들어가 같은 위치에 서보니 과거에는 책장이 시야를 막고 있었다. 다른 기록과 대조해 날짜 착오인지 거짓말인지 판단한다.

이 예시는 기능 검증용 퍼즐이다. 사건 전체의 범인 특정에는 시간표·접근 기회·행동 증거가 별도로 필요하다.

### 1.2 제작 조건

| 구분 | 조건 |
|---|---|
| 인원 | 2명 |
| 숙련도 | A: C++ 4/10, OpenGL 0/10 / B: C++ 2/10, OpenGL 0/10 |
| 기간 | 2~3주. 아래 일정은 10~15개 작업일 기준이며 실제 가용 시간에 맞춰 조정 |
| 기반 | C++, OpenGL, 현재 폴더의 Visual Studio 프로젝트 |
| 모델링 | 모델링 자산 없이 시작. 평면·상자·단순 인물 도형 사용 |
| 사운드 | FMOD 사용 예정. 음성 녹음·생성 없이도 진행 가능 |
| 외부 모델 | 필요할 때 Assimp로 가져옴. 기본 도형 단계의 선행 조건은 아님 |
| 최종 목표 | 5~10분 동안 시작→조사→추론→결말까지 진행 가능한 사건 하나 |

### 1.3 기능의 우선순위

| 반드시 완성 | 핵심이 연결된 다음 추가 | 이번 범위에서 제외 |
|---|---|---|
| 1인칭 이동, 벽 충돌, 물체 조사 | FMOD 환경음·효과음 | 전투, NPC 이동 AI |
| 한글 대화, 증거 수첩, 최종 제출 | Assimp 외부 모델 | 실시간 낮밤, 넓은 마을 |
| 현재/과거 3D 상태 전환, 시야 퍼즐 | 같은 공간의 잔향을 최대 3개로 확장 | 과거 시뮬레이션, 과거 물체 조작 |
| 가장자리 안개, 짧은 흡입 전환 | 안전성을 확인한 카메라 전진 | 볼류메트릭 안개, 고급 모션 블러 |
| 결말, 재시작, 제출 폴더 | 단순 광원과 색감 보강 | 음성 연기, 복잡한 애니메이션, 저장/불러오기 |

안개와 흡입 연출은 사용자 지정 요소다. 어려우면 가장자리의 단순한 움직이는 무늬와 시야각 변화로 줄여서 구현한다. 이 문서의 선택 기능은 과제의 별도 필수 조건이 확인되면 우선순위를 조정한다.

## 2. 현재 작업 폴더에서 확인한 출발점

2026-09-30에 프로젝트 파일과 일부 소스를 읽어 확인한 내용이다. 현재 빌드를 실행해 성공 여부까지 검증한 것은 아니다.

| 항목 | 확인 내용 | 개발 시작 시 작업 |
|---|---|---|
| 솔루션 | Pratice_Grapic.slnx | 두 PC에서 열리는지 확인 |
| 프로젝트 | Pratice_Grapic.vcxproj | x64 구성으로 시작 |
| 실행 소스 | x64 구성에서 Pratice_10.cpp가 포함되고 다른 실습 main 소스들은 제외됨 | 게임용 main은 하나만 빌드되도록 구성 |
| 기본 파일 | base_code.cpp는 x64 빌드에서 제외됨 | 완성된 게임 기반으로 오해하지 않고 초기화 코드를 참고 |
| 그래픽 | 소스가 OpenGL 3.3 Core를 요청하고 GLFW·GLEW·GLM 사용 | 기존 설정을 활용해 창과 큐브부터 검증 |
| 라이브러리 | x64 Debug/Release에 GLEW·GLFW·OpenGL 링크 경로 존재 | 두 PC의 SDK·툴셋·실제 라이브러리와 맞는지 확인 |
| 런타임 DLL | glew32.dll 복사 빌드 이벤트 존재 | 실행 파일 옆 복사 여부 확인 |
| 셰이더 | GLSL_Pratice 아래 실습용 파일 존재 | 게임용 셰이더를 별도 경로에 둠 |

권장 진행: 기존 실습 파일을 남기고 `game/` 아래 게임 소스를 추가한다. 프로젝트에 새 게임 소스를 등록할 때 x64 Debug와 Release 모두에서 실습 main을 제외한다. 프로젝트 파일 변경은 A가 담당한다. 폴더를 만드는 것만으로 소스가 자동 등록되는 것은 아니다.

초기에 CMake 전환이나 자체 엔진 제작은 하지 않는다. 이미 두 PC에서 실행되는 빌드 방식 하나를 유지한다.

## 3. 전체 개발 순서

```text
P0 실행 환경·한글 출력 검증 ──┐
                            ├→ P2 3D 방·조사 → P3 과거 공간·시야 퍼즐
P1 사건 시간표·단서 설계 ────┘                          ↓
                                      P4 안개·흡입 전환
                                                   ↓
                                      P5 추론·결말 연결
                                                   ↓
                                      P6 콘텐츠·오디오 보강
                                                   ↓
                                      P7 테스트·제출 패키징
```

P0와 P1은 독립적으로 일부 진행할 수 있지만, 첫 3D 퍼즐의 배치와 대사는 함께 확인한다. 뒤 단계의 장식 작업 때문에 앞 단계의 미완성 기능을 방치하지 않는다.

### 역할 원칙

- **A:** 프로젝트 설정, 렌더링, 카메라, 충돌, 상태 전환과 기능 통합.
- **B:** 사건 자료, 대사·증거 데이터, 물체 배치, 간단한 UI 내용, 수동 테스트.
- **공동:** 한글 UI 출력 실험, 첫 퍼즐 검증, 통합 실행과 오류 재현.
- B에게 텍스트 렌더러나 UI 엔진 전체를 독립적으로 맡기지 않는다. A가 만든 작은 함수에 데이터와 화면 내용을 붙이는 형태로 시작한다.
- 매 작업일 끝에 두 사람 모두 같은 버전을 실행한다. 기능이 끝나면 구현자가 상대에게 조작법과 제한을 설명한다.

## 4. 단계별 작업 명세와 통과 기준

### P0. 실행 기반과 한글 UI — 1~2일차

**입력:** 기존 실습 프로젝트, 두 개발자의 PC.

작업:

1. 원본 실습을 보존하고 게임용 실행 파일의 시작점을 정한다.
2. x64 Debug에서 빈 창과 단색 도형을 실행한다.
3. 셰이더 파일을 찾지 못했을 때 파일 경로와 오류를 출력하도록 한다.
4. 한글 한 문장과 버튼 하나를 화면에 띄운다. 폰트와 텍스트/UI 라이브러리는 작은 실험으로 선택한다.
5. C++ 소스 인코딩과 선택한 라이브러리의 문자열 형식을 맞춘다. 프로젝트의 Unicode 설정만으로 한글이 그려진다고 가정하지 않는다.
6. 실행 파일 기준 리소스 경로를 정하고 IDE 밖에서도 같은 파일을 읽게 한다.
7. 필요한 개발 환경과 실행 방법을 `docs/BUILD_AND_RUN.md`에 기록한다.

**산출물:** 빈 게임 실행 파일, 한글 출력 화면, 실행 방법.

**통과 기준:** 두 PC에서 실행되고 한글이 깨지지 않는다. x64 Release에서도 창과 리소스 로딩을 확인한다.

**막힐 때:** 게임 기능을 더 붙이지 말고 빌드·폰트 문제를 해결한다. 이 단계에서 Assimp와 FMOD를 동시에 도입하지 않는다.

### P1. 사건과 첫 퍼즐을 종이로 완성 — 1~3일차

**입력:** 기획서 v1.2의 인물과 잔향 규칙.

작업:

1. 실제 사건 순서와 각 인물의 위치를 표로 만든다.
2. 누가 정확히 기억하고, 무엇을 잊었고, 무엇을 의도적으로 숨기는지 별도로 적는다.
3. 첫 퍼즐은 현재/과거 책장 배치와 창밖 목격 위치로 정한다.
4. 그 과거 장면이 언제인지 입증할 날짜·순서 단서를 정한다. 가려진 시야만으로 다른 날의 목격까지 부정하지 않는다.
5. 마지막 생존 확인, 범행 가능 시간, 출입 경로, 사인·흉기, 다른 용의자의 배제 근거를 채운다.
6. 마라의 동기와 방문 사실만으로 유죄가 결정되지 않는지 확인한다.
7. 필수 단서를 모두 읽은 사람이 잔향의 새 능력이나 마지막 자백 없이 해답을 설명할 수 있는지 종이 테스트한다.

**산출물:** `docs/CASE_TIMELINE.md`, `docs/EVIDENCE_MAP.md`.

**통과 기준:** 첫 퍼즐이 논리적으로 성립한다. 전체 사건은 P5 콘텐츠 입력 전까지 범인 특정 근거를 완성한다.

**막힐 때:** 용의자와 장소를 더 만들지 않는다. 단서 연결을 수정한다. 미확정 사건을 완성된 정답 데이터처럼 코드에 고정하지 않는다.

### P2. 걷고 조사할 수 있는 방 — 2~4일차

작업:

1. 바닥·벽·창·책상을 상자로 배치하고 깊이 테스트와 원근 투영을 사용한다.
2. WASD 수평 이동과 마우스 시점을 구현한다. 수직 회전은 제한하고 대각선 이동 속도를 정규화한다.
3. 플레이어를 단순한 부피로 취급해 벽·책장과 충돌하게 한다. 점프와 계단은 넣지 않는다.
4. 화면 중앙에서 광선을 쏴 조사 가능한 물체를 찾는다.
5. 가장 가까운 가림 물체까지 확인해 벽 너머 NPC나 증거를 선택하지 못하게 한다.
6. 가까운 대상에만 이름과 `E 조사` 안내를 보여준다.
7. 대화가 열리면 마우스 시점·이동을 멈추고 UI 입력을 받는다.

**산출물:** 상자로 된 방, NPC 하나, 조사 물건 하나.

**통과 기준:** 시작→NPC 대화→물건 조사→증거 카드 획득이 된다. 벽을 통과하거나 멀리 있는 물건을 집지 않는다.

### P3. 잔향 공간과 첫 시야 퍼즐 — 4~6일차

작업:

1. 같은 방에 현재 배치와 과거 배치를 정의한다.
2. 개발용 전환 키로 먼저 즉시 전환을 검증한다. 연출은 나중에 붙인다.
3. 물체의 표시·위치와 충돌·조사 가능 여부를 같은 시점에 바꾼다.
4. 과거의 인물은 정지 모형으로 두고 대화·물체 이동은 허용하지 않는다.
5. 현재 위치와 시점을 저장하고, 과거는 지정된 안전한 위치에서 시작한다.
6. 목격 지점을 포함한 범위에서 걸어 다니며 창문과 책장에 의한 가려짐을 확인한다.
7. 돌아오면 저장한 현재 위치와 시점으로 복원한다.
8. 잔향에서 관찰한 내용은 수첩에 기록하되 증언의 진위는 자동 판정하지 않는다.

**산출물:** 현재/과거 한 쌍, 목격 위치, 모순을 확인할 수 있는 대사.

**통과 기준:** 다른 개발자가 설명 없이 두 배치의 시야 차이를 확인한다. 왕복 10회 후에도 위치·물체·증거 상태가 유지된다.

### P4. 가장자리 안개와 흡입 연출 — 6~7일차

작업 순서: 가장자리 안개 → 시야각 보간 → 장면 교체 연결 → 여유가 있으면 짧은 카메라 전진.

| 진입 구간 | 초깃값 | 동작 |
|---|---|---|
| 시작 | 0~0.2초 | 테두리 안개가 모이고 이동·시점·중복 진입 입력을 잠시 차단 |
| 끌림 | 0.2~0.6초 | 시야각을 약 65도에서 57도로 좁히고 안개 무늬를 안쪽으로 흐르게 함 |
| 교체 | 약 0.65초에 한 번 | 과거 배치·충돌·안전한 시작 위치 적용 |
| 안정화 | 0.85~1.2초 | 시야각을 원상 복구하고 조작 재개 |
| 과거 유지 | 탐색 중 | 바깥쪽 약 15~20%에 옅은 안개, 중앙은 선명 |
| 이탈 | 약 0.6~0.8초 | 짧은 역전환 후 현재 위치·시점 복원 |

시간과 시야각은 확정된 품질 기준이 아니라 실제 화면에서 조정할 시작값이다. 테두리 안개는 중앙을 가리지 않으므로 공간 교체가 완전히 숨겨지지는 않는다. 색감 변화와 함께 의도적인 순간 전환으로 처리하고, 이를 감추려고 필수 단서를 흐리게 만들지 않는다.

**산출물:** 정상 연출과 움직임을 줄인 전환 옵션.

**통과 기준:** 반복·빠른 키 입력으로 상태가 꼬이지 않고, 과거 탐색 중에는 카메라 확대·전진이 멈춘다. UI 글자는 안개 위에 선명하게 보인다.

### P5. 추론과 결말까지 연결 — 7~10일차

작업:

## 6. 게임 루프·입력·상태 관리

### 6.1 한 프레임의 작업 순서

```text
이벤트 수집
→ 경과 시간 계산
→ 현재 입력 모드에 따라 조작 처리
→ 잔향 전환과 게임 상태 업데이트
→ 이동·충돌·조사 대상 계산
→ 활성 3D 장면 렌더링
→ 가장자리 안개 오버레이
→ 조준점·대화·수첩 등 UI
→ 화면 표시
```

이동과 전환은 프레임 수가 아니라 경과 시간을 기준으로 한다. 창 최소화·중단점 이후 큰 경과 시간이 들어와 벽을 통과하지 않도록 처리한다. 화면 높이가 0인 동안 투영 비율 계산이나 렌더링을 건너뛰고, 크기가 복구되면 갱신한다.

### 6.2 키와 입력 우선순위 제안

| 입력 | 탐색 | 잔향 내부 | UI 또는 전환 중 |
|---|---|---|---|
| WASD·마우스 | 이동·시점 | 이동·시점 | 이동 중지, UI에서만 커서 사용 |
| E | 물건 조사·NPC 대화 | 관찰 기록 | 버튼 선택 또는 무시 |
| R | 가까운 잔향에 진입 | 잔향에서 나가기 | 전환 중 중복 요청 무시 |
| Tab | 수첩 | 수첩 | 수첩 닫기. 전환 중은 무시 |
| Esc | 일시정지 메뉴 | 일시정지 메뉴 | 최상위 UI 닫기. 전환 중에는 메뉴 요청을 완료 후 처리 |

기존 실습의 Esc 즉시 종료 동작을 그대로 가져오지 않는다. 게임 종료는 메뉴에서 선택한다. 키 이름은 구현 시 바꿀 수 있지만 모든 안내 화면과 일치해야 한다.

월드 상태와 UI 상태를 나눈다. 과거에서 수첩을 열었다고 현재로 돌아가는 버그를 방지한다. 일시정지·포커스 상실 동안 전환 타이머도 멈추고, 복귀 시 마우스의 첫 좌표 차이를 초기화해 시점이 튀지 않게 한다.

### 6.3 잔향 상태 전이

```text
Present → Entering → Echo → Exiting → Present
```

- Present에서 허용된 잔향을 조사한 경우에만 Entering으로 간다.
- 진입 직전에 현재 카메라 위치·방향을 한 번 저장한다.
- 진행도가 교체 지점을 넘을 때 한 번만 과거 장면과 충돌을 적용한다. 특정 프레임의 정확한 시간 일치로 판정하지 않는다.
- Echo에서 조작을 재개한다. 과거 NPC는 정지해 있다.
- 이탈 교체 지점에서 현재 장면과 저장한 카메라를 복원한다.
- 상태별 진입 처리는 한 번만 실행한다. 과거가 없거나 ID가 잘못되면 요청을 거부하고 현재에 남는다.

전환 완료 시에는 계산 오차가 남지 않게 목표 시야각과 안개 강도를 명시적으로 설정한다. 반복 진입으로 기본 시야각이나 위치가 누적 변경되지 않게 한다.

### 6.4 카메라 요구 항목 점검 — 확대·자전·이동·공전·부모

2026-10-01 사용자 요청을 반영한 설계 점검이다. 자전·공전은 카메라의 회전 기준점을 뜻하며 태양계나 물체 애니메이션을 의미하지 않는다. 아래의 ‘기존 계획’은 구현 완료라는 뜻이 아니다. ‘부모’는 부모-자식 변환 관계로 해석한다.

| 항목 | 게임에 넣을 위치 | 실제 카메라 동작 | 현재 문서 상태 | 체크리스트 |
|---|---|---|---|---|
| 확대 | 잔향 진입의 흡입 연출 | 카메라 위치를 유지하며 FOV를 좁혀 화면 확대 | 기존 계획 있음 | V001~V003 |
| 자전 | 1인칭 마우스 둘러보기 | 눈 위치는 그대로 두고 yaw·pitch로 방향 회전 | 기존 계획 있음 | M006~M008 |
| 이동 | 방 탐색, 목격자가 서 있던 자리로 이동 | WASD로 카메라를 포함한 플레이어 위치 이동 | 기존 계획 있음 | M002~M005, M009~M012 |
| 공전 | 획득한 단서의 별도 입체 상세보기 | 단서 중심을 바라보며 카메라가 일정 거리에서 주위를 회전 | 새로 추가할 후보. 아직 필수 확정 아님 | K005~K011 |
| 부모 | 플레이어에 붙은 눈 카메라, 상세보기의 회전 중심 | 부모 변환과 카메라의 로컬 변환을 합쳐 월드 변환 계산 | 기존 계획에 명시되지 않아 구조 추가 제안 | K001~K004 |

**확대:** FOV 축소는 투영 변화이고, 카메라 전진은 위치 이동이다. 두 동작은 원근감 변화가 다르다. 현재 요구는 카메라 기준으로 해석했으므로 FOV로 분류하며, 물체의 모델 행렬을 키우는 스케일 변환까지 구현했다고 설명하지 않는다. 수업의 ‘확대’가 모델 스케일을 뜻하는지는 실제 평가 기준이 있어야 확정할 수 있다.

**자전:** 카메라가 자기 위치에서 방향만 바꾼다. 이를 위해 카메라 월드 위치를 원점 중심으로 회전시키면 안 된다. 개발용 좌표 표시로 마우스만 움직일 때 위치가 그대로인지 확인한다.

**공전:** 물건을 회전시키는 것과 구별한다. 단서는 고정하고 카메라 위치가 그 중심 주위를 움직여야 한다. 가장 자연스러운 추가 지점은 수첩에서 이미 획득한 잔향 조각이나 봉인 도구를 3D로 살펴보는 화면이다. 마우스 드래그로 앞면·옆면의 각인이나 파손 면을 관찰하게 할 수 있다. 첫 구현은 큐브 하나로 충분하며 실제 단서 문양은 사건 설계에서 정한다.

과거 공간 전체를 자유 공전시키면 벽 뒤를 쉽게 보거나 목격 위치에서 벗어나 시야 퍼즐을 우회할 수 있다. 따라서 공전은 별도의 단서 상세보기 후보로 둔다. 세계의 원본 단서 위치·회전은 변경하지 않고 표시용 복사본과 전용 카메라를 사용한다. 상세보기를 닫으면 기존 탐색 위치·방향·FOV·입력 모드로 돌아온다.

**부모:** 움직임 종류가 아니라 변환을 물려주는 구조다. 클래스 상속과도 다르다. 첫 구현은 다음 정도로 제한한다.

```text
PlayerRoot          # WASD 위치, 몸의 좌우 방향
└─ EyeCamera        # 로컬 눈높이, 위아래 시선

InspectionPivot     # 상세보기 단서의 중심, 공전 각도
└─ InspectionCamera # 중심에서 떨어진 로컬 거리
```

플레이어의 부모 위치를 바꾸면 카메라가 같은 만큼 움직이고, 카메라의 로컬 눈높이는 유지된다. 부모의 yaw와 카메라의 pitch를 중복 적용하지 않는다. 카메라 부모에는 확대·축소 스케일을 넣지 않는다. 공전 중심도 스케일된 모델의 자식으로 무조건 연결하지 말고 별도의 변환으로 둔다.

열벡터 행렬 관례를 사용하는 경우 핵심 관계는 다음과 같다.

```text
CameraWorld = ParentWorld * CameraLocal
View = inverse(CameraWorld)

# 기본적으로 -Z를 바라보는 카메라의 공전 배치 예시
CameraWorld = Translate(pivot) * RotateYaw * RotatePitch * Translate(0, 0, radius)
```

위 행렬은 개념 확인용이다. 현재 프로젝트에서 사용할 좌표계와 카메라 정의를 일관되게 정한 뒤 적용한다. 공전 pitch는 극점까지 가지 않도록 제한하고, radius는 양수로 유지한다.

발표 때는 확대 시 FOV, 자전 시 방향, 이동 시 위치, 공전 시 대상과의 거리, 부모 관계에서 로컬 눈높이를 개발용 표시로 보여주면 차이가 명확하다. 교수의 평가 충족 여부나 실제 구현 완료를 미리 주장하지 않는다.

## 7. 렌더링과 안개 구현 지침

### 7.1 기본 3D

정점 위치는 3차원 좌표를 사용하고 모델·뷰·투영 행렬을 구분한다. 현재/과거 데이터는 같은 방의 공통 좌표계를 사용한다. 깊이 테스트로 책장 뒤의 물체가 가려져야 한다. 창은 처음에는 유리 없이 벽의 구멍으로 만들어 투명 정렬 문제를 줄인다.

과거 물체 전체를 반투명하게 만들지 않는다. 벽과 책장이 투명해지면 시야를 검증하는 퍼즐이 무너진다. 과거의 색감과 화면 가장자리 안개로 상태를 구별한다.

### 7.2 화면 가장자리 안개

첫 구현은 화면 전체를 덮는 사각형 위에 가장자리만 알파가 생기는 셰이더를 그린다. 복잡한 후처리용 프레임버퍼는 필수가 아니다.

개념식:

```text
uv = 화면 내 0~1 좌표
edgeDistance = 가장 가까운 화면 테두리까지의 거리
edgeMask = 1 - smoothstep(0, borderWidth, edgeDistance)
alpha = clamp(edgeMask * strength * movingPattern, 0, maxAlpha)
```

`movingPattern`은 천천히 변하는 간단한 무늬다. 첫 버전에서는 몇 개의 부드러운 파형만으로 시작할 수 있다. 무늬의 진행 방향은 실제 화면에서 확인해 진입 시 중심으로 흐르게 조정한다. 원형 무늬를 쓰면 화면 가로세로 비율도 보정한다.

그리기 순서는 불투명 3D → 안개 → UI다. 안개를 그릴 때 깊이 쓰기를 끄고 알파 블렌딩을 켠 뒤, 다음 프레임의 3D 그리기 전에 상태를 복원한다. UI는 안개 색과 투명도를 상속하지 않게 한다.

### 7.3 흡입감

보간 함수로 시야각을 좁혔다가 원래 값으로 돌린다. 첫 구현에서는 카메라의 실제 위치를 움직이지 않아도 된다. 추가 전진은 충돌과 안전한 시작 위치를 검증한 뒤 짧게 적용한다. 카메라 회전·진동·블러를 동시에 더하지 않는다.

전환은 시각 효과이며 새로운 이동 수단이 아니다. 벽을 뚫거나 조사 대상 밖으로 나갈 수 없어야 한다. 효과를 줄인 옵션에서는 안개만 짧게 전환한다.

## 8. 사건·증거 데이터 작성 규칙

첫 버전은 C++ 구조체와 배열로 정의해도 된다. JSON 파서나 별도 편집기를 만드는 것을 선행 작업으로 삼지 않는다. 문자열 표시는 내용, 연결은 고유 ID를 기준으로 한다.

| 데이터 | 최소 필드 |
|---|---|
| SceneObject | id, 도형 종류, 위치·회전·크기, 색, 충돌 여부, 조사 ID |
| EchoScene | id, 현재 장소 ID, 과거 물체 목록, 안전한 시작 위치, 관찰 ID |
| Evidence | id, 제목, 내용, 유형(관찰/문서/증언), 출처 |
| DialogueNode | id, NPC ID, 본문, 선택지, 필요한 증거/추론, 획득 증거 |
| DeductionRule | id, 주장 문구, 필요한 증거 ID 집합, 해금 결과 |
| GameState | 획득 증거, 완료 추론, 대화 진행, 결말 여부 |

증거 소유만으로 추론을 자동 완료하지 않는다. 플레이어가 주장과 근거를 제출해야 한다. 근거 선택 순서는 정답에 영향을 주지 않게 한다. 같은 증거를 두 번 고를 수 없게 하고, 입력 데이터의 존재하지 않는 ID를 개발 중에 검사한다.

논리 검토용 작성 표:

| ID | 실제 사실 | NPC 주장 | 잔향에서 보이는 것 | 다른 근거 | 허용 결론 | 아직 모르는 것 |
|---|---|---|---|---|---|---|
| 예: VIS_01 | 과거 창 앞에 책장이 있었다 | 창밖에서 책상을 봤다 | 시야를 가리는 책장 | 배치 변경일 기록 | 해당 과거 배치에서는 목격 불가능 | 어느 날짜를 말했는지, 고의인지 |

잔향의 내부 날짜는 개발 자료에 적되 플레이어 UI에 자동 표시하지 않는다. 게임 안에서 날짜를 알 근거가 있을 때만 수첩에 관찰 결과로 남긴다. 기존 증언도 유지하고 갱신 대사는 별도 기록으로 추가한다.

대화와 단서의 선행 조건은 그래프로 확인한다. 증거 A를 얻으려 B가 필요하고 B를 얻으려 A가 필요한 순환을 만들지 않는다. 중요한 추론마다 오답 이후에도 다시 조사 가능한 경로를 둔다.

## 9. 리소스와 라이브러리 도입 순서

1. 기존 GLFW·GLEW·GLM으로 창·카메라·도형을 실행한다.
2. 한글 UI 도구와 폰트를 선택하고 실제 문장을 출력한다. 선택한 도구의 공식 통합 절차를 확인한다.
3. FMOD를 별도 간단한 재생 확인으로 검증한 뒤 게임에 연결한다.
4. Assimp가 필요하면 작은 외부 모델 하나를 가져오는 확인을 거친 뒤 추가한다.
5. 각 라이브러리의 버전·CPU 아키텍처·빌드 설정·필요 DLL을 문서에 기록한다.

버전, FMOD의 구체적인 이용 자격, 개별 에셋의 허가는 이 문서에서 검증하지 않았다. 도입 시 공식 문서와 해당 자료의 조건을 확인한다. 사용자가 비상업 사용을 전제로 한다는 요구를 에셋 선정에 반영한다.

리소스 기준 경로는 실행 파일 옆 `assets/`로 통일하는 것을 권장한다. 개발 빌드에서도 같은 배치를 사용한다. 셰이더나 폰트를 못 찾으면 빈 화면으로 계속 진행하지 말고 대상 경로를 로그에 남긴다.

## 11. 협업과 변경 관리

- 버전 관리를 도입한다면 Git을 사용한다. 현재 폴더의 저장소 상태는 이 문서 작성에서 검증하지 않았다.
- 소스·셰이더·콘텐츠 데이터·배포 가능한 에셋·문서는 공유하고, 개인 IDE 상태·중간 빌드 출력은 공유 대상에서 분리한다.
- 프로젝트 파일과 공유 헤더 변경은 먼저 상대에게 알린다. A가 프로젝트 설정을 통합한다.
- 한 작업은 “NPC 대화 열기”, “현재 위치 복원”처럼 직접 확인 가능한 크기로 나눈다.
- 작업 완료 기록에는 바뀐 기능, 확인 방법, 알려진 문제를 남긴다.
- 상대가 수정한 파일을 통째로 덮어쓰지 않는다. 병합 후 두 PC에서 실행한다.
- 기획 변경은 먼저 사건 표와 기획서에 반영하고, 영향을 받는 대사·배치·정답을 함께 수정한다.

작업 카드 양식:

```text
작업 ID / 제목:
담당자:
선행 작업:
수정할 파일:
사용자가 보게 될 결과:
완료 확인 방법:
남은 문제:
```

## 12. 테스트 체크리스트

단순 색 변경마다 자동 테스트를 만들 필요는 없다. 순수한 증거 판정과 상태 전환은 작은 검사로 확인하고, 공간·연출·추리 공정성은 실제 플레이로 검증한다.

### 실행과 조작

- [ ] 두 PC의 x64 Debug/Release에서 실행된다.
- [ ] IDE 밖에서도 셰이더·폰트·에셋을 찾는다.
- [ ] 한글·줄바꿈·버튼 영역이 정상이며 긴 증언이 잘리지 않는다.
- [ ] 대각선 이동, 모서리 충돌, 창 크기 변경, 포커스 복귀가 정상이다.
- [ ] 수첩·대화 중 이동하지 않고 닫은 뒤 시점이 튀지 않는다.
- [ ] 벽 너머 대상은 조사할 수 없다.

### 잔향과 시야

- [ ] 현재/과거 각각 시야를 막는 물체와 충돌이 일치한다.
- [ ] 목격 위치에서 정해진 가림 관계를 직접 확인할 수 있다.
- [ ] 과거 인물은 정지해 있고 현재 상태를 변경하지 못한다.
- [ ] 10회 왕복해도 시야각·위치·안개가 누적되지 않는다.
- [ ] R 연타, 전환 중 Tab·Esc, 포커스 상실 후 복귀가 상태를 깨뜨리지 않는다.
- [ ] 벽 옆에서 진입해도 벽 안에 나타나지 않는다.
- [ ] 과거를 걸어 다닌 뒤에도 현재의 원래 위치로 안전하게 돌아온다.
- [ ] 화면 비율을 바꿔도 중앙과 UI가 안개에 가려지지 않는다.
- [ ] 전환 중만 흡입감이 있고 탐색 중에는 시야가 안정된다.

### 추리와 진행

- [ ] 증거 획득이 중복되지 않고, 없는 증거 ID는 개발 중에 발견된다.
- [ ] 올바른 주장·근거 조합만 통과하며 선택 순서는 영향을 주지 않는다.
- [ ] 필수 증거 없이 최종 정답을 통과하지 않는다.
- [ ] 오답·대화 재방문 후에도 결말에 도달할 수 있다.
- [ ] NPC의 기억 손실 범위가 정해져 있고 임의로 확대되지 않는다.
- [ ] 잔향에 나오지 않은 사실을 정답의 필수 전제로 요구하지 않는다.
- [ ] 정답을 모르는 플레이어가 범인뿐 아니라 증거 연결을 설명할 수 있다.
- [ ] 재시작하면 이전 획득·추론·결말 상태가 남지 않는다.

외부 테스트 기록은 “못 풀었다” 대신 어느 단서를 보았고, 어떤 결론을 내렸고, 어디서 막혔는지 적는다. 답을 먼저 알려준 뒤 테스트를 완료했다고 처리하지 않는다.

## 13. 제출 패키지와 발표

권장 패키지:

```text
GameSubmission/
  Game.exe
  필요한 런타임 DLL
  assets/
  README.md
  CREDITS.md
  KNOWN_ISSUES.md
```

실제 실행 파일 이름과 필요한 DLL은 빌드 결과에 맞춰 작성한다. SDK 폴더 전체를 복사하지 않는다. 배포 환경에 필요한 C++ 런타임도 깨끗한 PC에서 확인한다. 자료 출처와 사용 조건은 실제 포함 파일에 맞춘다.

발표 시연 순서:

1. 1인칭 이동과 원근·깊이 가림을 보여준다.
2. NPC의 목격 증언을 확인한다.
3. 안개와 흡입 연출을 거쳐 과거에 들어간다.
4. 직접 목격 위치로 이동해 책장 때문에 시야가 막힘을 보여준다.
5. 현재로 돌아와 다른 기록과 함께 추론을 제출한다.

설명 문장: “기억이 불완전한 주민의 증언을, 변하지 않는 과거의 3D 공간과 대조하는 추리 게임입니다.” 교수의 평가는 별도 평가 기준에 따르며, 이 시연은 구현한 3D 기능과 추리의 관계를 보여주기 위한 것이다.

최종 완료 기준은 기능 개수가 아니라 **처음 실행한 사람이 이동·조사·잔향 관찰·추론·결말을 모두 경험할 수 있는가**다.
