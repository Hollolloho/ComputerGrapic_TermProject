# 게임 디자인 패턴 적용 안내

학습 목표는 기능을 구현하며 설계 이유를 이해하는 것이다. 패턴 개수나 클래스 수를 목표로 삼지 않는다.

| 패턴·개념 | 적용 부분 | 첫 구현 | 확장할 조건 |
|---|---|---|---|
| 상태 기계 / State | Present·Entering·Echo·Exiting과 입력 모드 | enum과 전환 함수, 진입 처리를 한 번만 실행 | 상태별 동작이 커지면 State 클래스로 분리하며 전후 코드 비교 |
| 컴포넌트 구성 | 물체의 변환·표시·충돌·조사 | 작은 데이터 구조를 조합 | 여러 물체에 독립 기능이 반복될 때 모듈화 |
| Observer | 증거 획득 후 수첩·안내 갱신 | 먼저 획득 함수 한 곳에서 UI 상태 갱신 | 구독자가 늘면 콜백 구독·해제를 구현 |
| Event Queue | 전환 중 메뉴 열기 요청 | pendingPause 하나를 완료 후 처리 | 서로 다른 지연 이벤트가 여러 개 필요할 때 큐로 확장 |

enum 상태 분기만 만든 것을 다형성 State 패턴 전체 구현이라고 설명하지 않는다. 단순한 직접 호출만으로 Observer를 구현했다고 표시하지 않는다. 실제 추가 전에는 학습 계획이고 추가 후에는 사용한 구조와 확인 결과를 기록한다.

## 필수 상태 학습 순서

1. 월드 상태와 UI 모드를 분리한다.
2. 허용된 전이만 처리한다.
3. 진입·교체·이탈 처리를 중복 호출하지 않는다.
4. 중복 입력과 복귀를 실제 실행한다.
5. 코드를 함께 읽고, 상태가 늘어났을 때 필요한 분리만 결정한다.

## 부모와 컴포넌트

카메라 부모는 클래스 상속과 다르다. ParentWorld × CameraLocal이라는 변환 관계다. 컴포넌트 학습을 위해 ECS나 범용 장면 그래프를 만드는 것은 필수가 아니다.

## 작업 목록과 연결

C006~C007·O005: 부모 변환. E001~E016: 상태 관리. G018~G020: 증거 갱신. Observer·범용 큐는 필요할 때 선택적으로 추가하며 카메라5가지나 잔향 자체보다 먼저 만들지 않는다.

각 패턴을 도입할 때 '기존 문제가 무엇이었는지 / 수정한 흐름 / 같은 행동을 확인한 방법'을 짧게 기록한다. 기능과 무관한 전체 코드 재작성은 피한다.
